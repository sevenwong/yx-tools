# Cloudflare 优选 IP 测速方案（fast_select.py）

> 本文记录 2026-11-02 ~ 11-03 这轮改造的结论。目的：三个月后不用读代码就能知道  
> 「为什么这么设计、参数怎么调、出问题先看哪里」。
>
> 对应文件：`fast_select.py`（主任务）、`cloudflare_speedtest.py`（被复用的库）、  
> `~/.crontab.final`（定时任务最终版）。

---

## 一、三条硬约定

这三条是这套方案的地基。改任何一条之前，先想清楚代价。

### 1. 主任务只有一个，就是 fast_select.py

定时任务只跑 `fast_select.py`。`cloudflare_speedtest.py` 退回成「库」的角色，  
提供候选池构建、WS 握手验证、TTFB + 机房探测、机房分散选择、上传函数——  
**不再单独执行**。日志一律进 `logs/`，按天分文件。

为什么：两个脚本同时当主任务，就会抢同一个 `result.csv`、抢同一份候选池文件，  
还会各自上传一次、互相把对方的池子清掉。整体替换之后，这个问题从根本上不存在。

### 2. 宁可这次不上传，也不要把线上池子搞差

两道闸，任何一道没过就整次放弃，**线上旧池保持原样**：

- **第一道（粗筛）**：筛选出的候选不足 5 个，直接退出，连 CSV 都不写。
- **第二道（细筛）**：WS 握手验证通过的 IP 不足 5 个，放弃上传。

为什么：上传带「先清空再写入」的语义。如果只勉强凑出 2 个就清空上传，  
线上池会从 10 个缩到 2 个——比「这周不更新」糟糕得多。旧池虽然旧，但至少可用。

### 3. 改完必须实测，不许说「应该好了」

改脚本、改定时任务，三步走：先备份 → 再实际跑一遍 → 拿日志说话。  
没有能证伪的证据，就不算完成。定时任务改完，必须真的等到它自己触发一次，  
而不是手动跑一遍就宣布生效。

## 二、为什么要换掉原来的测速

原方案调用 CloudflareST 这个第三方二进制做下载测速，问题是**串行**：  
一个 IP 测完再测下一个，单个 IP 要跑满窗口 2~10 秒。而它的停止条件是  
「凑够 N 个达标的就停」，**没有上限**。达标率通常只有 6% 左右，  
要凑 20 个就得把几百个候选全测一遍——10 月 30 日那次从 22:40 跑到 00:10，**90 分钟**。

现在的做法：用 curl 自己下载测速，8 路并发 + 硬性时间截止，实测 **200~400 秒**。

注意一个容易误解的点：**换掉的只是「下载测速」这一步**，不是整个项目。  
候选池怎么来的、怎么判断一个 IP 能不能真当代理、怎么按机房分散、  
怎么上报给 Worker，全部还是 yx-tools 原来的实现，  
`fast_select.py` 直接 `import` 过来复用。所以这个仓库依然是核心，  
只是不再需要那个 CloudflareST 二进制了。

## 三、测法：两段式

### 第一段：并发测速，2 秒一个，只用来排名

200 个候选，8 路并发，每个下载 2 秒就掐断，算平均速度，排序。

**这一段的数字不能当真实速度用。** 8 路并发共享同一条出口带宽，  
每个 IP 只分到 1/8，绝对值必然偏低。它的唯一作用是：从 200 个里挑出前 30 个  
值得进一步测的。

耗时：200 ÷ 8 × 2 秒 ≈ **52 秒**。

### 第二段：串行复测，5 秒一个，用来判门槛

对前 30 名逐个单独下载，每个 5 秒。这时候是独占带宽，数字才是真实单流速度。

耗时：30 × 5 秒 ≈ **151 秒**。

### 为什么是「固定时长」而不是「固定字节」

这是这次改造最关键的一个认知转变。

旧测法固定下 10MB 就算完。问题在于：链路快的时候，10MB 只要 **0.4 秒**就下完了，  
而这 0.4 秒全程都在 TCP 慢启动阶段（连接刚建立，窗口还没涨起来）。  
结果就是**越快的链路被压得越狠**。

本机到 Cloudflare 边缘的往返延迟约 200 毫秒，跑满带宽需要约 8 个往返、  
也就是 1.7 秒左右。固定 5 秒能把这段「预热期」摊成固定比例，快慢 IP 之间才可比。

同一 IP、同一分钟的实测对照（分钟级差异，非严格对照实验）：

| 测法            | 报出的速度     |
| ------------- | --------- |
| 下满 10MB 就停（旧） | 7.5 MB/s  |
| 下满 3 秒        | 17.6 MB/s |
| 下满 5 秒        | 32.1 MB/s |
| 下满 10 秒       | 37.5 MB/s |

结论：5 秒是拐点。8 秒只比 5 秒多 7%，但要多花 60% 的时间，不划算。

### 一个必踩的坑：缺 Referer 会被 429

直接用 curl 请求测速端点，会返回 429，响应体只有 1 字节。  
不检查状态码的话，算出来的「速度」是假的（几乎为 0），还会让人误判成「链路太差」。

**必须带 `Referer: https://speed.cloudflare.com/` 这个请求头。** 加上就正常 200 出流量。  
CloudflareST 二进制自带合规请求头，所以只有自己重写测速时才会撞上这个问题。  
脚本里已经对非 200 的状态码做了拦截和统计（会打印状态码分布、429 会单独告警）。

## 四、参数怎么调

| 参数                | 当前值       | 含义                     | 调它要注意什么                                           |
| ----------------- | --------- | ---------------------- | ------------------------------------------------- |
| `--top`           | 200       | 按建连延迟排序后，保留多少个进下载测速    | 调小会漏掉「延迟稍高但带宽大」的 IP；调大只会拖长第一段                     |
| `--max-rtt`       | 300       | 建连延迟硬门槛（毫秒）            | 实测候选延迟存在断层：P75 在 295ms，之后直接跳到 1200ms+。300 正好切在断层上 |
| `--conc`          | 8         | 第一段并发数                 | 这是「并发下载数」，不是延迟探测线程数。链路越好可以适当加，但并发越高每个 IP 分到的带宽越少  |
| `--dur`           | 2         | 第一段每个 IP 下载几秒          | 只用于排名，可以短                                         |
| `--serial-dur`    | 5         | 第二段每个 IP 下载几秒          | **判门槛用，不能低于 5**，否则又掉回慢启动陷阱                        |
| `--deadline`      | 240       | 从开始测速算起的硬上限（秒）         | 到点不再派发新任务                                         |
| `--serial-budget` | 180       | 第二段允许超出 deadline 的额外秒数 | 30 个 × 5 秒 = 150，留了 30 秒余量                        |
| `--min-speed`     | 6.0       | 速度门槛（MB/s）             | 见下一节，这个数字的含义变了                                    |
| `--pick`          | 10        | 最终写入线上池的 IP 数          |                                                   |
| `--min-pick`      | 5         | 候选/通过数不足几个就整次放弃        | 对应的就是「第二条硬约定」                                     |
| `--per-colo`      | 2         | 同一机房最多留几个              | 防止某个机房占满名单，一个机房出问题就整池不可用                          |
| `--bytes`         | 400000000 | 测速请求的字节数               | 必须大于「时长 × 带宽」，保证是被时长掐断而不是下完了                      |

### 关于 6MB/s 这个门槛

**换测法之后，这个数字的含义变了。**

- 旧测法下，同一个 IP 报 6MB/s，实际单流大约要 15~25MB/s 才算达标（因为被低估）。
- 新测法下，报 6MB/s 就是真实单流 **48Mbps**，看 4K 视频够用。

所以门槛保留了 6.0，但它现在是一个「刚好够用」的标准，而不是之前的「偏严」的标准。  
如果觉得太松，往上调；往下调则要接受画质下降。

**已知风险**：如果某个周五晚上本机链路本身很差（比如单流只能跑到 3~5MB/s），  
那门槛会全灭，当次不更新池子。这是设计如此，不是故障，日志里会出现  
「没有 IP 达到速度门槛」。

## 五、整条流程的时间账

11-03 02:00 的实测（200 个候选）：

| 阶段                         | 耗时          |
| -------------------------- | ----------- |
| 候选池构建（撒点 → 探活 → 测延迟 → 截断）  | 27 秒        |
| 第一段并发测速（200 个 × 2 秒 ÷ 8 路） | 52 秒        |
| 第二段串行复测（30 个 × 5 秒）        | 151 秒       |
| TTFB + 落地机房探测              | 13 秒        |
| **合计**                     | **约 243 秒** |

其中候选池那 27 秒里，大头是「探活」——每个地址等 3 秒超时，绕不开。  
1200 个随机地址里只有约 900 个是活的，剩下的是没分配的地址。

## 六、候选池是怎么从 1200 个筛到 200 个的

不是查表，全是远程实测：

1. **取官方网段清单**，只留下历史上实测能连上 Worker 的那几段（避开会被拒 error 1034 的段）。
2. **撒点**：在这些段里随机生成 1200 个具体地址（跳过每段首尾保留地址），按段的历史可用性分配名额。
3. **探活**：64 个一组同时试连，每个等 3 秒。1200 个里约 900 个是活的，其余是没分配的地址。
4. **测延迟**：200 个一组并发测建连耗时，按快到慢排序。约 150 个测不出结果（超时或中途失败）。
5. **按段配额截断**：取前 200 个，但每段设上限，防止某一段占满名额。

所以 1200 → 200 ≈ 300 个空地址 + 150 个测不出延迟 + 其余被配额和延迟排序挤掉。

## 七、失败时先看哪里

按这个顺序看，能省很多时间：

1. **日志里有没有「没有 IP 达到速度门槛」** → 是链路问题，当次不更新池子，属正常兜底。
2. **有没有出现 429** → 请求头丢了 Referer，本轮速度全部不可信，直接修代码。
3. **有没有「候选不足」或「少于 min-pick」** → 候选池构建出了问题（网段清单、探活、延迟门槛）。
4. **总耗时是否远超 300 秒** → 看串行复测是不是跑满了预算；预算耗尽时未复测的会降级成「替补」，  
   仍然写进 CSV 供 WS 被拒时补位，但不参与门槛判定。
5. **上传是否真的生效** → **不要看接口返回里的 `addedAt` 字段**，那个字段每次请求都返回当前时间，  
   不是真正的写入时间，看它必然误判。要验证就看线上池的 **IP 内容有没有变**。

## 八、回滚

`~/.crontab.final` 里保留了旧的命令行，前面用 `# [已停用 2026-11-02]` 注释掉。  
回滚只需两件事：删掉新的那行，把旧行开头的 `# ` 去掉。

改完务必用 `crontab` 装回去，并且**装之前先复查一遍**：确认没有哪行「停用注释」漏写了 `#`，  
否则那行会变成真任务，跟着一起跑。
